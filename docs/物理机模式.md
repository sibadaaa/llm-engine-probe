# 物理机（裸机）模式指南

> **一句话**：同一套探测/对比测试，既可以跑在 Docker 容器里（默认），也可以**直接在物理机上跑 vLLM**——
> 只是把"起实例/停实例/看状态/py-spy"这几步从 `docker run` 换成 `exec 本机进程`，
> 其余探针、套件、报告、对比全部原样复用，产物结构与字段口径完全一致。
>
> 本文讲**物理机模式怎么用、和 Docker 怎么一一对应、出问题怎么查**。工具箱总体说明见 [README](../README.md)。

---

## 0. 设计原则（先看这三条）

1. **不需要改探针工具包**：`probe/` 是纯标准库实现，本来就既可跑在容器内也可跑在宿主机上；
   `scripts/probe_all.sh`、`scripts/run_suite.sh`、`scripts/report.sh`、`python3 -m probe *` 与运行方式无关，
   它们只认 `--port` / `--run-dir`（另有可选的 `--runtime` / `--log-file`，只用于标注运行方式与指定外部日志）。
2. **不需要改厂商适配层**：`vendors/*.sh` 的**设备可见性环境变量**（`CUDA_VISIBLE_DEVICES` / `HIP_VISIBLE_DEVICES` /
   `ASCEND_RT_VISIBLE_DEVICES` / `ZE_AFFINITY_MASK`）、**厂商环境脚本 prelude**（DTK / Ascend `set_env.sh`）、
   **SMI 遥测命令**、**trace 规则包**在物理机上同样生效；只有 Docker 专属的**设备直通参数**
   （`--device` / `--gpus` / `--group-add`）在 host 模式下被忽略。
3. **产物不搬家**：host 模式下运行目录、`run_meta.json`、`serve.log`、`traces/`、`suite_results.json`、
   `REPORT.md` 的位置和结构都与 Docker 模式相同 —— 因此两个模式的结果可以直接 `probe compare` 并排看。

切换运行方式只有一个开关：

```bash
RUNTIME=host          # 物理机/裸机直接跑（默认 RUNTIME=docker）
```

`RUNTIME` 大小写不敏感，并支持别名：`container → docker`、`bare` / `native → host`；
脚本里也可以用 `--host` / `--docker` / `--runtime host` 临时覆盖 `.env`。

---

## 1. 适合谁

* 没有 Docker / Docker daemon 不可用（或不允许）的机器，但想用这套工具箱做 vLLM 全流程探测；
* 想**排除容器开销**，测"裸机 + 驱动 + vLLM"的真实性能基线；
* 已有装好 vLLM 的 Python 环境（venv/conda/系统解释器），不想再构建镜像；
* 需要在同一台机器上**对比"容器内 vs 裸机"**两种部署方式的差异。

> 什么时候不建议用 host 模式：需要 `docker-compose` 观测栈（Prometheus/Grafana/OTel，见 README §8）
> 或需要容器隔离/可回滚的快速实验时，Docker 模式更省事。

## 2. 前置条件

### 2.1 硬件与驱动

| 项 | 要求 | 自查命令 |
|---|---|---|
| 加速卡 | 与 vLLM 版本配套的 GPU/DCU/NPU（参照各厂商 vLLM 发行说明） | `hy-smi` / `nvidia-smi` / `rocm-smi` / `npu-smi` / `xpu-smi` |
| 驱动/运行时 | 已安装对应厂商驱动与用户态运行时（ROCm/CUDA/CANN/oneAPI） | 同上，能正常列出设备 |
| 设备权限 | 当前用户能访问设备节点（`/dev/kfd`、`/dev/dri`、`/dev/davinci*`、`/dev/nvidia*` 等） | `ls -l /dev/kfd /dev/dri/*` |

> 物理机模式**不负责装驱动**。驱动装不对时先跑 `make host-check`，它会明确告诉你哪一项没过。

### 2.2 Python 环境与 vLLM

物理机模式直接调用本机的 Python，建议用**独立的 venv/conda 环境**，避免污染系统 Python：

```bash
# 示例：已有环境（把路径换成你的实际解释器）
which python3 && python3 -V
python3 -c "import vllm, torch; print('vllm', vllm.__version__); print('torch', torch.__version__)"

# 如果 vLLM 装在某个 venv 里，用 HOST_PYTHON 指过去：
#   .env 里写 HOST_PYTHON=/path/to/venv/bin/python
```

要求：

* `HOST_PYTHON` 指向的解释器**必须能 `import vllm` 和 `import torch`**；
* vLLM 版本与 Docker 模式使用的一致（或至少同一大版本），否则性能数字不可比；
* torch/vLLM 的厂商适配（如 ROCm 版 PyTorch、vllm-ascend）要装对——这是**环境准备**，不是本工具箱的职责。

### 2.3 厂商环境脚本与环境变量（prelude）

容器模式下，`start_vllm.sh` 会在启动服务前执行厂商环境脚本（如 hygon 的
`. /opt/dtk/env.sh`、`. /src/tools/dcu/env.sh`）。物理机模式用 `HOST_PRELUDE_FILES` 达到同样效果：

```bash
# .env
# 空格分隔的 token，按书写顺序执行：
#   K=V      → export 该环境变量
#   其它路径 → 存在则 source（不存在静默跳过）
HOST_PRELUDE_FILES="DTK_ROOT=/mnt/game/host-runtime/dtk2604 /home/lyh/z100-vllm/tools/dcu/env.sh"
```

* **顺序有意义**：token 按从左到右执行。上面的例子先 `export DTK_ROOT=…`，再 source 依赖它的
  `env.sh`；如果把两者顺序写反，脚本里的变量会取不到值。
* 不 source 这些脚本时，典型症状是 `import torch` 报
  `ImportError: librocm_smi64.so.2: cannot open shared object file`（hygon）或找不到 CANN 库（Ascend）。
* Ascend 一般写 `HOST_PRELUDE_FILES=/usr/local/Ascend/ascend-toolkit/set_env.sh`（路径以机器为准）。
* prelude 里的环境变量会**被拉进**后续启动的 vLLM 进程（`serve_launch.sh` 里可见）。
* **预检、状态与版本探测使用同一套环境**：`host-check`、`status` 的 import/版本探测，以及
  `start_vllm.sh` 写 `run_meta.json` 时的 host 版本探测，都会先按顺序应用 prelude、再叠加 host 模式的
  `PYTHONPATH`（`SRC_DIR` + 项目根 + `TRITON_INSTALL_DIR`），与 `serve_launch.sh` 完全一致；
  因此 prelude 配好后，这些检查不会因为"没有 source 环境"而假失败。
* `make host-check` 的 `prelude` 项会区分两类 token：`K=V` 视为环境变量 export（不作为文件检查），
  文件路径才检查是否存在；缺文件只 warn，不影响启动预检的 fail 判定。

### 2.4 模型权重

模型就放在本机磁盘上，`MODEL` 填**宿主机的绝对路径**（物理机模式没有"容器内路径"这层映射）：

```bash
# .env
MODEL=/mnt/game/models/Qwen3.8-27B-FP8
SERVED_NAME=qwen3.8-27b
```

* 路径对 `HOST_PYTHON` 可读即可；
* 投机解码的 `DRAFT_MODEL` 也填宿主机路径；
* `EXTRA_MOUNTS` / `GAME_DIR` 不参与（没有容器挂载这层概念）；
* `SRC_DIR` 在 host 下仍然有用：如果 vLLM 是源码 checkout 安装的，把它设成 checkout 路径，
  它会被加入 host 模式的 `PYTHONPATH`（但不再有容器里的 `/src` 只读挂载语义）。

### 2.5 系统限制（容易踩的坑）

Docker 模式下这些限制由 `docker run --ulimit` / `--shm-size` 给出；物理机模式需要你在**宿主机/启动 shell**里满足：

```bash
# 1) 锁页内存：vLLM 的 pinned memory 需要；太小会报 "Failed to allocate ... pinned memory"
ulimit -l unlimited          # 永久生效：/etc/security/limits.conf 里加 memlock unlimited

# 2) 栈大小：大模型/大 batch 下 8MB 可能不够
ulimit -s unlimited          # 或至少 65536

# 3) /dev/shm：多进程/TP>1 时 NCCL/RCCL/HCCL 会用共享内存；容器默认 64MB 常不够，
#    宿主机一般较大，但小规格虚机/NUMA 机器仍可能不足
df -h /dev/shm               # 建议 >= 显存级数量（例如 >= 16G 更好）
#   /etc/fstab 里：tmpfs /dev/shm tmpfs defaults,size=64G 0 0

# 4) 文件句柄 / 线程数（大并发时）
ulimit -n 65535 2>/dev/null || true
```

可选（性能敏感时）：

* **NUMA 绑定**：多路 CPU 机器上用 `numactl --cpunodebind=… --membind=…` 包住启动命令（写进 `HOST_SERVE_ENTRYPOINT`）；
* **大页**：部分 ROCm/CUDA 场景可配 HugePages 提升 TLB 命中；
* **频率/功耗策略**：确认功耗墙与散热，避免"双稳态"被误归因为 vLLM（工具会提示慢态占比）。

> 注意：`ulimit` 是**进程继承**的。要先在同一个 shell 里 `ulimit` 再 `make up-host`；
> 或者用 systemd 单元（见 §10）把 `LimitMEMLOCK=infinity` 等固化下来。

### 2.6 不需要 Docker

host 模式**完全不调用 docker**（`host_check.sh` 也不会把"没有 docker"当作失败项）。
`IMAGE` / `CONTAINER` / `MODE=exec` / `EXEC_CONTAINER` / `EXTRA_MOUNTS` / `GAME_DIR` /
`docker-compose` / 观测栈 compose 在 host 模式下都不参与。

## 3. 配置 `.env`

和 Docker 模式共用同一份 `.env`，只是多了一组以 `HOST_` 开头的变量：

```bash
cp .env.example .env
$EDITOR .env
```

### 3.1 与运行方式相关的变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `RUNTIME` | `docker` | `docker` = 容器（默认）；`host` = 物理机裸机直接跑 |
| `HOST_PYTHON` | `python3` | 本机 Python 解释器（**必须能 `import vllm` / `import torch`**） |
| `HOST_SERVE_ENTRYPOINT` | 空 | 留空 = 自动用 `HOST_PYTHON` 执行 vLLM CLI 入口（`vllm.entrypoints.cli.main`）；特殊入口/包装命令时才自定义 |
| `HOST_PRECHECK` | `1` | 启动前是否自动跑 `host_check.sh` 预检（`0` 关闭；临时跳过用 `--skip-check`） |
| `HOST_PRELUDE_FILES` | 空 | 启动前按顺序执行的环境 token（空格分隔）：`K=V` → export，其它路径 → 存在则 source（DTK/Ascend/ROCm 环境） |
| `HOST_STOP_TIMEOUT` | `60` | `stop` 时等待优雅退出的秒数，超时后清理进程组 |
| `HOST_VLLM_PATTERN` | 见 `.env.example` | host 模式查找/兜底清理 vLLM 进程的正则（默认覆盖 vLLM CLI/EngineCore/APIServer） |
| `PYSPY_BIN` | 空 | 本机 py-spy 可执行文件（留空自动从 `PATH` 找） |
| `MODEL` | （必填） | 宿主机上的模型目录绝对路径 |
| `PORT` | `8100` | vLLM 监听端口（探针访问用，仍刻意避开现网 8000） |
| `PROBE_LEVEL` | `steps` | 观测档位：`off`/`basic`/`steps`/`deep`/`kernel`，与 Docker 模式完全相同 |

### 3.2 最小可用配置示例

```bash
# 运行方式
RUNTIME=host
HOST_PYTHON=/home/me/venv-vllm/bin/python
# prelude：K=V 先 export，再 source 依赖它的脚本（顺序有意义）
HOST_PRELUDE_FILES="DTK_ROOT=/opt/dtk2604 /opt/dtk/env.sh"
HOST_PRECHECK=1

# 模型与端口（宿主机路径）
MODEL=/mnt/models/Qwen3.8-27B-FP8
SERVED_NAME=qwen3.8-27b
PORT=8100
TP=4
EAGER=1

# 档位
PROBE_LEVEL=steps

# 厂商可见性仍然生效（厂商由 VENDOR=auto 自动探测，也可显式指定）
VISIBLE_DEVICES=0,1,2,3
```

> Makefile 不硬编码运行方式：`.env` 里写 `RUNTIME=host` 后，`make up/down/status/probe/...` 全部
> 自动走物理机模式。想**临时**切一次时用 `make up RUNTIME=host`，或直接用 `*-host` 目标
> （`make up-host`、`make probe-host` 等，它们显式带 `--host`，不依赖 `.env`）。

## 4. 预检：`make host-check`

```bash
make host-check                 # 人读格式（末尾有 pass/warn/fail 汇总）
make host-check JSON=1          # 机器可读 JSON（写到 PROBE_OUTDIR/RUN_DIR，默认 runs/latest/host_check.json）
make host-check JSON=1 RUN_DIR=runs/hc   # 指定 JSON 落盘目录
bash scripts/host_check.sh      # 脚本直调（等价）
bash scripts/host_check.sh --quick          # 跳过耗时项（import vllm/torch、GPU SMI 采样）
bash scripts/host_check.sh --start          # 启动前快速预检：只跑 fail 级核心项（隐含 --quick）
bash scripts/host_check.sh --json --outdir runs/latest   # 指定 JSON 落盘目录
bash scripts/host_check.sh --skip-vllm-import --skip-gpu # 离线/无 GPU 的结构自检
```

预检项与处理办法（`--json` 版本会逐项给出 `id/name/level/ok/detail/hint`）：

| id | 检查项 | 它在查什么 | 不通过怎么办 |
|---|---|---|---|
| `os` | 操作系统 | Linux 内核/发行版/架构 | 一般只作信息记录 |
| `host_python` | 宿主 Python 解释器 | `HOST_PYTHON` 是否存在、可执行 | 改 `HOST_PYTHON` 指向正确 venv/conda 解释器 |
| `python_version` | Python 版本 | 版本是否满足 vLLM 要求 | 换较新的解释器/虚拟环境 |
| `vllm` | vLLM 可导入 | `import vllm` 及版本号 | 装/修好 vLLM；注意用的是 `HOST_PYTHON` 而不是系统 `python3` |
| `torch` | PyTorch / 加速器 | `import torch`、CUDA/ROCm(HIP)/NPU 可用性、设备数 | 装厂商适配版 torch；hygon 记得 `HOST_PRELUDE_FILES` source DTK |
| `gpu_smi` | GPU 遥测（SMI） | 厂商 SMI 能否列出设备（hy-smi/nvidia-smi/…） | 装驱动、加设备权限（`video` 组等）、检查 `VISIBLE_DEVICES` |
| `model_path` | 模型目录 | `MODEL`（及草稿模型）是否存在、可读 | 换成宿主机上真实路径 |
| `port` | 端口可用 | `PORT` 是否被占用 | 换端口，或先停掉占用进程/实例 |
| `curl` | curl | 探针依赖的基础命令 | `apt/yum install curl` |
| `py_spy` | py-spy 火焰图工具 | `PYSPY_BIN`/PATH 里是否有 py-spy | 安装 py-spy 或设 `PYSPY_BIN`（缺它只影响火焰图） |
| `ptrace` | ptrace 权限（yama） | `/proc/sys/kernel/yama/ptrace_scope` | 见 §9 的 py-spy 权限处理 |
| `ulimit` | ulimit 资源限制 | memlock / stack / nofile 等 | 按 §2.5 调整（或 systemd 固化） |
| `shm` | `/dev/shm` 共享内存 | 容量是否够 TP>1 通信 | 调大 `/dev/shm`（§2.5） |
| `prelude` | 厂商 prelude 环境 | `HOST_PRELUDE_FILES` 的 token：`K=V` 会被 export；文件路径检查是否存在 | 修路径；Ascend 检查 `set_env.sh` 位置；确认 `K=V` 的变量名/值写对 |

说明：

* 退出码：**0 = 没有 fail 级问题**（warn/info 不影响）；**1 = 有 fail 级项**；2 = 参数用法错误。
  启动时（`HOST_PRECHECK=1`）若预检非零，`start_vllm.sh` 会拒绝启动并提示用 `--skip-check` 跳过；
* **口径与真实启动一致**：`--quick` 只是跳过耗时项、`--start` 只跑核心项（都是原有语义，不变）；
  而 `vllm` / `torch` 的 import 与版本探测，会在**先应用 prelude（`K=V` export + 文件 source）并叠加
  host `PYTHONPATH`（`SRC_DIR` + 项目根 + `TRITON_INSTALL_DIR`）** 的环境里执行——与
  `serve_launch.sh` 同一套环境，不会因为没 source 厂商脚本而假失败；
* `--json` 产物 `<outdir>/host_check.json` 的 `kind` 为 `vllm-probe-hostcheck`，包含
  `versions`（python/torch/vllm/设备数/SMI）、`summary`（pass/warn/fail 计数）与 `checks` 逐项结果，
  可直接留档或接 CI；
* 预检**不修改系统**，只读；`--quick` 只跳过耗时项，`--start` 只跑核心项，适合每次启动前快检；
* 没有 GPU 的机器/离线环境可以用 `--skip-gpu` / `--skip-vllm-import` 做**结构自检**
  （自测脚本 `tests/host_mode_selftest.sh` 就是这么跑的）。

## 5. 启动 / 停止 / 状态 / 日志

### 5.1 启动

```bash
# 推荐：Makefile 目标
make up-host                              # 默认 steps 档；用 LEVEL=deep|kernel 覆盖
make up-host LEVEL=kernel                 # kernel 档（profiler + 逐层 NVTX）
make up-host RUN_DIR=runs/manual          # 指定运行目录

# 脚本直调（等价；两种写法都行）
RUNTIME=host scripts/start_vllm.sh
RUNTIME=host scripts/start_vllm.sh --level deep
scripts/start_vllm.sh --host --level steps
scripts/start_vllm.sh --runtime host --level steps    # 等价写法
RUNTIME=host scripts/start_vllm.sh --dry-run     # 只打印将执行的命令，不启动
RUNTIME=host scripts/start_vllm.sh --skip-check  # 跳过自动预检
scripts/start_vllm.sh --host --docker            # 用 --docker 可强制覆盖 .env 的 RUNTIME
```

#### 5.1.1 用启动模板（可选）

换厂商/模型/并行度时不必反复手改 `.env`：

```bash
hosts/vllm-host.sh list                                      # 列出全部模板
hosts/vllm-host.sh show vendor/hygon scenario/tp4-prod spec/dflash
hosts/vllm-host.sh check vendor/hygon scenario/tp4-prod     # 物理机预检（带模板变量）
hosts/vllm-host.sh dry-run vendor/hygon scenario/tp4-prod spec/dflash   # 只打印命令
hosts/vllm-host.sh up   vendor/hygon scenario/tp4-prod spec/dflash      # 启动
```

模板是 `hosts/<类别>/*.env` 的 shell 片段，按「厂商 → 场景 → 量化/投机 → 部署形态」叠加；
显式环境变量（如 `TP=2`）优先于模板，模板优先于 `.env`。入口、模板索引、systemd/外部实例/PD/多机
骨架见 [`hosts/README.md`](../hosts/README.md)。`show`/`dry-run` 不会启动实例，可安全复核。

启动后 host 模式在运行目录里落这些文件（与 Docker 模式相同位置，只是含义变成"本机进程"）：

| 文件 | 内容 |
|---|---|
| `serve.pid` | 本机 vLLM 进程 PID（setsid 会话组长；`stop` 按它找进程组） |
| `serve.pgid` | 进程组 ID（`stop` 时按组清理，避免 TP worker 残留；通常等于 `serve.pid`） |
| `serve_launch.sh` | 实际执行的启动脚本（含 prelude source、环境变量、完整命令；可直接复现） |
| `serve.log` | 引擎日志（探针解析的对象） |
| `traces/` | torch profiler trace 落盘目录（kernel 档；host 下就是运行目录里的这个路径） |
| `run_meta.json` | 含 `"runtime": "host"` 与 `"host": {python, python_version, vllm_version, torch_version, hostname, kernel}` |

日志实时看：

```bash
tail -f runs/<时间戳>/serve.log
make watch                     # 逐 step 实时解析（host 下走文件模式）
RUNTIME=host scripts/watch_steps.sh --summary --run-dir runs/<时间戳>
```

> host 模式下 `watch_steps.sh --docker` **不可用**（会明确报错退出），因为不存在容器日志；
> 用默认的文件模式即可。

### 5.2 停止

```bash
make down-host                          # 温和停止（SIGTERM 整个进程组，HOST_STOP_TIMEOUT 秒后 SIGKILL）
RUNTIME=host scripts/stop_vllm.sh       # 等价
RUNTIME=host scripts/stop_vllm.sh --run-dir runs/<时间戳>   # 指定运行目录（默认 $RUN_DIR/最新 runs/*）
RUNTIME=host scripts/stop_vllm.sh --timeout 30             # 覆盖等待秒数
RUNTIME=host scripts/stop_vllm.sh --rm                     # host：无需删除容器，保留 pid 记录与 run dir
```

> ⚠️ host 下 `--kill-exec` 等价于**按 `HOST_VLLM_PATTERN` 杀本机所有匹配 vLLM 的进程**（包括别的实验），
> 请先 `ps` 确认；只想停本工具起的实例时用默认方式（按 `serve.pgid` 整组终止）。
> 停止后 `serve.pid`/`serve.pgid` 会保留在运行目录里（便于事后确认），要彻底清理由你手动 `rm -rf`。
>
> 🕒 **停止后默认会等显存回落**（轮询本机 SMI，最长约 60s；本机还有其它显存占用时可能等满）。
> 物理机上的假实例/无显存占用的调试，或同机还有其它任务不想等时，可以跳过：
> `PROBE_SKIP_VRAM_WAIT=1 RUNTIME=host scripts/stop_vllm.sh`（等价 `--no-vram-wait`）；
> 用 make 时：`PROBE_SKIP_VRAM_WAIT=1 make down-host`。
>
> 🔎 **外部实例不会被 `stop` 误停**：`stop_vllm.sh` 只按运行目录里的 `serve.pid`/`serve.pgid`
> 停止**本工具启动**的实例（`--kill-exec` 的整机 pattern 清理除外，见上）。不是 `start_vllm.sh`
> 启动的实例（例如 systemd/手工启动，没有 `serve.pid`）不在管理范围内，请用它自己的方式停止；
> 要探测它请用 `probe_all.sh --runtime host --log-file …`（见 §6.1）。

停不掉时（例如 TP worker 卡死）：

```bash
# 先看还有哪些相关进程（正则来自 HOST_VLLM_PATTERN）
ps -eo pid,pgid,etime,args | grep -E "$HOST_VLLM_PATTERN" | grep -v grep
# 再确认无其它实验后，按进程组清理
kill -TERM -<serve.pgid>; sleep 10; kill -KILL -<serve.pgid>
# 最后确认显存回落
make gpu-sample                        # 或直接看本机 SMI
```

### 5.3 状态

```bash
make status-host
RUNTIME=host scripts/status.sh --port 8100
RUNTIME=host scripts/status.sh --port 8100 --run-dir runs/<时间戳>   # 指定运行目录
```

输出会先标出**运行方式：host（物理机）**，再给 PID、端点 `/health` `/v1/models` `/metrics` 状态、
关键指标（running/waiting、KV 使用率、前缀缓存命中、投机解码接受率等）与最近日志摘要，
与 Docker 模式的 `make status` 一一对应。与外部实例相关的几点：

* **外部实例（非本工具启动）**：没有 `serve.pid`、但本机 `pgrep` 命中 vLLM 进程时，`status` 会显示
  「外部实例（非本工具启动）」并列出匹配进程，而不是提示"未运行/先 start_vllm.sh"。
  这类实例的版本信息只能按 `.env` 的 `HOST_PYTHON` 环境推测，未必等于它实际使用的解释器。
* **端点检查是只读的**：`/start_profile` 探活改为 `GET`（不再发 `POST`），不会对正在跑的生产实例
  产生副作用；若实例带 `--api-key` 启动，设置 `VLLM_API_KEY` 后 `/v1/models` `/metrics` 的端点检查
  会带 `Authorization: Bearer …`（探测产物里的 key 会打码；`cmd.txt`/`args.txt`/`serve_launch.sh`
  等启动类产物按启动命令原样记录，含 `--api-key` 时请保护运行目录权限）。
* **运行目录的选择**：不指定 `--run-dir` / `RUN_DIR` 时，按目录 **mtime** 取 `RUNS_DIR` 下最新的一个
  （不再是目录名字符串排序，避免 `runs/optmatrix-…` 这类名字压过真正刚写入的目录）；要精确定位
  某次运行请显式给 `--run-dir`。

### 5.4 一次完整的 host 冒烟流程

```bash
make host-check            # ① 预检
make up-host               # ② 起实例（等 /health 就绪）
make status-host           # ③ 看状态
make probe-host            # ④ 全链路探测 + 报告
tail -f runs/<时间戳>/serve.log
make down-host             # ⑤ 停实例
```

## 6. 跑完全相同的测试

host 模式下所有探针命令与 Docker 模式**完全一样**，区别只是 `make` 目标带 `-host`
（或脚本前加 `RUNTIME=host`），因为部分脚本需要知道按哪种方式找日志/进程。

### 6.1 全链路探测与报告

```bash
make probe-host
# 等价：RUNTIME=host scripts/probe_all.sh --port 8100 --level steps
# 深层：make probe-host LEVEL=kernel
# 带 GPU 遥测 + py-spy：
RUNTIME=host scripts/probe_all.sh --with-gpu-sample --with-pyspy

# 探测"不是本工具启动"的外部实例（日志不在 <RUN_DIR>/serve.log）：
RUNTIME=host scripts/probe_all.sh --runtime host --port 8100 \
  --run-dir runs/live-host --log-file /var/log/vllm/serve.log --skip-trace

cat runs/<时间戳>/REPORT.md
```

* `--runtime docker|host`：显式标注运行方式；不写时按 `.env` 的 `RUNTIME`（默认 docker）。
* `--log-file PATH`（或 `.env` 的 `PROBE_LOG_FILE`）：用于外部实例。日志会被**复制为
  `<RUN_DIR>/serve.log`** 再做 step 级解析；`run_meta.json` 的 `serve_log` 字段也会记录它，
  `report` 在 `<RUN_DIR>/serve.log` 不存在时会回退读这份外部日志。
* **自动补 run_meta**：没经过 `start_vllm.sh` 的实例，`probe_all.sh` 会补一份最小 `run_meta.json`，
  包含 `runtime`、`host{...}`（本机 python/vLLM/torch 版本等）、`vendor`/`vendor_label` 等，
  因此报告开头会正确显示「物理机（host）」，而不是默认的 docker。
* **运行目录**：不指定 `--run-dir` 时按目录 mtime 取最新（见 §5.3）；外部实例建议单独给一个
  `RUN_DIR`，避免和之前的运行混在一起。
* **step 级观测**：需要日志里有 `Iteration(...)` 明细。外部生产启动脚本（不在本仓库）若支持
  `ITER_DETAILS=1`，可用它打开 `--enable-logging-iteration-details`；否则档位再高，step 级和
  报告第 3 节也会是空的。

### 6.2 标准化套件与跨模式对比

```bash
make suite-host                 # 8 场景 → suite_results.json（与 Docker 同一 schema）
make compare A=runs/docker/suite_results.json B=runs/host/suite_results.json OUT=runs/COMPARE-docker-vs-host.md

# 探测外部实例时显式标注运行方式（没有 run_meta 也会自动补）：
RUNTIME=host scripts/run_suite.sh --runtime host --port 8100 --run-dir runs/live-host
```

`run_suite.sh` 新增 `--runtime docker|host`；没有 `run_meta.json` 时也会自动补一份最小 run_meta，
因此 `suite_results.json` 的 `engine` 段里始终有 `runtime`（host 时还有 `host` 环境信息），
`make compare` 的 A/B「运行方式」不会再一律误标成 docker。

### 6.3 算子级 trace

```bash
make up-host LEVEL=kernel       # 必须以 kernel 档启动（端点 /start_profile 才存在）
make trace-host                 # 抓 trace + 自动归因
# 产物：runs/<时间戳>/traces/rank*.pt.trace.json.gz、trace_summary.json、key_averages.json
```

### 6.4 CPU 侧 py-spy

```bash
RUNTIME=host scripts/pyspy.sh --mode dump
RUNTIME=host scripts/pyspy.sh --mode flame --duration 30
# 产物：runs/<时间戳>/pyspy/ 下的栈快照与 SVG 火焰图
```

> 物理机直接对 PID 采样，不需要 Docker 的 `--cap-add SYS_PTRACE`；但 Linux 的 yama 限制可能仍要求
> `ptrace_scope` 放宽或以 root 运行（见 §9）。

### 6.5 GPU 遥测

```bash
make gpu-sample                 # 各厂商 SMI → gpu_telem.jsonl
RUNTIME=host scripts/gpu_sample.sh --duration 60
```

### 6.6 stat logger 插件（最深一层）

```bash
# .env 里 PROBE_PLUGIN=1，或：
PROBE_PLUGIN=1 make up-host
python3 -m probe plugin --outdir runs/<时间戳> --file runs/<时间戳>/probe_steps.jsonl
```

host 模式下插件会被安装到运行目录的 `.probe_plugins/`（`PYTHONPATH` 指向它），**不会污染**
`HOST_PYTHON` 的 site-packages；只需要 `HOST_PYTHON -m pip` 可用。插件 JSONL 直接写到
`<RUN_DIR>/probe_steps.jsonl`，与 Docker 模式下 `/logs/probe_steps.jsonl` 对应。

### 6.7 报告刷新与产物清单

```bash
make report RUN_DIR=runs/<时间戳>     # 或 RUNTIME=host scripts/report.sh --run-dir runs/<时间戳>
```

> 对外部实例刷新报告时，若 `<RUN_DIR>/serve.log` 不存在，`report` 会回退读取
> `run_meta.json` 的 `serve_log` 字段（`--log-file` / `PROBE_LOG_FILE` 写入的那份日志），
> 因此不必先把日志复制进运行目录。

> **再次强调**：上面这些命令**不需要任何修改**就能在 host 模式跑，因为它们读的是
> `--port` / `--run-dir` / 日志文件与 `/metrics`，与 vLLM 跑在容器还是宿主机无关。

## 7. 与 Docker 结果对比

两个模式的结果**可以且应该**直接对比，但必须满足可比性条件：

1. **同一模型、同一权重**（同精度、同量化）；
2. **同一 vLLM/torch 版本**（`run_meta.json` 的 `host` 字段与 Docker 模式的镜像内版本）；
3. **同一启动参数**（TP/`GPU_MEM_UTIL`/`MAX_MODEL_LEN`/`EXTRA_VLLM_ARGS`/投机解码配置）；
4. **同一观测档位**（`PROBE_LEVEL` 一致；`kernel` 档会关图模式，别拿它比吞吐）；
5. **同一测量窗口/负载**（套件用固定的 8 场景矩阵即可）。

```bash
make compare A=runs/<docker>/suite_results.json B=runs/<host>/suite_results.json OUT=COMPARE.md
```

对比报告会展示运行方式（`runtime: docker` vs `host`）以及各场景 TTFT/TPOT/E2E/吞吐/引擎差分。
外部实例只要在探测时显式给了 `--runtime host`（或 run_meta 完整），A/B 两侧的运行方式都会正确显示，
不会一边倒标成 docker。

> 📁 **建议显式给 `--run-dir`**：未指定时脚本按目录 **mtime** 选最新运行目录（见 §5.3），
> 刚生成的报告可能不是你预期的那次；对比/复现时把 A/B 路径写全最稳妥。

判读要点：

* **host 比 docker 快**：常见于容器设备直通/CPU 配额/页锁定带来的开销；看 p50/p99 与引擎侧 token 速率是否同向；
* **差异在噪声范围**：同一档位下重复跑 2~3 次再下结论（尤其 `steps`/`deep` 档日志/采样本身有开销）；
* **host 明显慢**：先查 `make host-check`、NUMA/频率/降频、`/dev/shm`、`ulimit`，
  再看报告第 8 节的自动归因（GEMM/通信/慢态占比）。

## 8. 「Docker 配方 → 物理机」迁移对照表

| Docker 里的做法 | 物理机（host）等价做法 | 说明 |
|---|---|---|
| `docker run <镜像> bash -lc '... vllm serve ...'` | 由 `HOST_PYTHON` 执行 vLLM CLI（serve 参数自动拼好），或 `HOST_SERVE_ENTRYPOINT` 自定义 | `serve_launch.sh` 里能看到最终命令 |
| `docker-compose.<vendor>.yml` 选厂商 | `hosts/vendor/<vendor>.env`（配合 `hosts/vllm-host.sh`） | 场景/量化/投机/部署模板见 [`hosts/README.md`](../hosts/README.md) |
| `--gpus all` / `--device /dev/kfd --device /dev/dri` / `--group-add video` | 不传任何参数；靠宿主机驱动 + 当前用户设备权限 | host 模式**忽略** Docker 设备直通参数 |
| `env: CUDA_VISIBLE_DEVICES=… / HIP_VISIBLE_DEVICES=… / ASCEND_RT_VISIBLE_DEVICES=…` | 同样生效（由 `VISIBLE_DEVICES` + 厂商 profile 生成） | 厂商可见性逻辑不变 |
| `-e VLLM_*` / `EXTRA_ENV` | 同样生效 | 探针观测开关完全一致 |
| `-v $PWD:/opt/vllm-probe:ro`（工具包挂载） | 不需要；直接在仓库目录里跑 `python3 -m probe` | 探针是纯标准库 |
| `-v <模型盘>:<容器内路径>` | 不需要；`MODEL` 直接填宿主机路径 | 无路径映射 |
| `-v <SRC_DIR>:/src:ro`（vLLM 源码） | 不需要挂载；设置 `SRC_DIR` 会把源码目录加进 host 模式的 `PYTHONPATH` | `run_meta.json` 仍记录版本 |
| `-v <RUN_DIR>:/logs`、`-v <TRACE_DIR>:/traces` | 不需要；直接写 `<RUN_DIR>/serve.log`、`<RUN_DIR>/traces/` | 产物路径相同，内容口径相同 |
| `-e` 厂商 prelude `bash -lc '. /opt/dtk/env.sh'` | `HOST_PRELUDE_FILES="DTK_ROOT=… /opt/dtk/env.sh"` | 空格分隔的 token 按顺序执行：`K=V` → export，路径 → source；start/status/host-check 共用同一套环境 |
| `--ipc=host` / `--shm-size=16g` | 宿主机 `/dev/shm` 即"共享内存"；用 `df -h /dev/shm` 确认足够大 | 见 §2.5 |
| `--ulimit memlock=-1` / `--ulimit stack=-1` | `ulimit -l unlimited` / `ulimit -s unlimited`（或 systemd `LimitMEMLOCK=infinity`） | ulimit 有继承性 |
| `--cap-add SYS_PTRACE`（py-spy 用） | 不需要容器 cap；直接采样本机 PID（yama 限制见 §9） | `RUNTIME=host scripts/pyspy.sh` |
| `-p 8100:8100` / `--network host` | 不需要端口映射；vLLM 直接监听 `PORT`（默认 `0.0.0.0:8100`） | 探针访问 `127.0.0.1:PORT` |
| `docker logs -f` | `tail -f <RUN_DIR>/serve.log`（`make watch` 逐 step 解析） | `--docker` 模式在 host 下不可用 |
| `docker stop` / `docker rm` | `make down-host` / `RUNTIME=host scripts/stop_vllm.sh`（SIGTERM → 超时清进程组） | PID 在 `serve.pid` / `serve.pgid` |
| `docker exec ... python3 -c`（容器内自检） | 直接 `HOST_PYTHON -c`（prelude 先 source） | 例如 §6.6 的插件自检 |
| `docker-compose` / `docker-compose.obs.yml` | 不参与；观测栈改为**外部 Prometheus 抓宿主机 `:PORT/metrics`** | 见 README §8 |
| `MODE=exec`（复用已有容器）/ `EXEC_CONTAINER` | 不参与；host 模式只管理自己启动的进程（外部实例用 `probe_all --runtime host --log-file … --port …` 只读探测） | `--kill-exec` 对应 host 的进程清理 |
| 镜像版本即 vLLM 版本 | `HOST_PYTHON` 环境里的 vLLM 版本，`run_meta.json` 记录 | 换环境=换版本 |

## 9. 故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `make host-check` 会不会因为没有 Docker 而失败 | host 模式本来就不调用 docker | 不会；host 模式就是给没有 Docker 的机器用的 |
| `import vllm` / `import torch` 失败 | `HOST_PYTHON` 指错解释器；vLLM/torch 没装；DTK/CANN 未 source | `HOST_PYTHON=/path/venv/bin/python`；用 `HOST_PRELUDE_FILES="DTK_ROOT=… /path/env.sh"` 按顺序 export/source；`make host-check` 现在会在同一环境里探测 |
| `ImportError: librocm_smi64.so.2: cannot open shared object file` | hygon DTK 环境未 source | `HOST_PRELUDE_FILES="DTK_ROOT=/mnt/game/host-runtime/dtk2604 /src/tools/dcu/env.sh"`（`K=V` 先 export，再 source 依赖它的脚本） |
| 启动后立刻退出，`serve.log` 里 `unrecognized arguments` | `EXTRA_VLLM_ARGS` 与本机 vLLM 版本不匹配 | 按 `run_meta.json`/`serve_launch.sh` 核对参数；临时去掉可疑参数 |
| `Failed to allocate ... pinned memory` / 锁页失败 | `ulimit -l` 太小 | `ulimit -l unlimited`（或 systemd `LimitMEMLOCK=infinity`） |
| 段错误 / 栈溢出 | `ulimit -s` 太小 | `ulimit -s unlimited` |
| TP>1 时卡住 / 通信初始化失败 | `/dev/shm` 太小、网卡/IB 环境、可见卡数不对 | `df -h /dev/shm`；确认 `VISIBLE_DEVICES` 与 `TP` 匹配；参考厂商 RCCL/NCCL/HCCL 文档 |
| 端口被占用 | 已有实例/其它服务占了 `PORT` | `make status-host`；`ss -ltnp` 过滤 `PORT`；换端口或停旧实例 |
| 显存不够 / 多实例互相挤兑 | 同卡上还有别的实例 | `make gpu-sample` 看 VRAM；停掉其它实例；物理机模式一次仍只建议跑一个实例 |
| py-spy 报权限错误（`ptrace_scope`） | Linux yama 限制 | `sudo sysctl -w kernel.yama.ptrace_scope=0`（临时）或以 root 运行；或给 py-spy 加 `CAP_SYS_PTRACE` |
| `stop` 后进程/显存没退 | 子进程/pgid 未清、SMI 缓存 | 按 `serve.pgid` 清进程组；`HOST_STOP_TIMEOUT` 调大；用本机 SMI 确认真实占用 |
| `stop` 要等约 60s 才返回 | 默认等显存回落；同机还有其它显存占用 | 不想等就跳过：`PROBE_SKIP_VRAM_WAIT=1 RUNTIME=host scripts/stop_vllm.sh`（或 `--no-vram-wait`） |
| `status` 显示「外部实例（非本工具启动）」 | 实例不是 `start_vllm.sh` 启动的（没有 `serve.pid`），但 `pgrep` 命中了 vLLM 进程 | 正常提示；用 `probe_all.sh --runtime host --log-file …` 只读探测，或用实例自己的方式（systemd 等）管理 |
| 报告/套件把 host 实例的运行方式标成 docker | 未指定 `--runtime host` 且运行目录没有 `run_meta.json`（旧行为默认 docker） | `probe_all.sh` / `run_suite.sh` 加 `--runtime host`；脚本会自动补最小 run_meta（runtime/host/vendor） |
| step 级为空 / 报告第 3 节空（外部实例） | 外部启动脚本没开 iteration 明细 | 外部脚本支持时用 `ITER_DETAILS=1` 打开 `--enable-logging-iteration-details`；或确认启动档位 ≥ `steps` |
| `host-check` 的 `vllm`/`torch` 与手动 source 后结果不一致 | 旧版预检没有 source prelude / 叠加 host `PYTHONPATH`（已修） | 现在预检与 `serve_launch.sh` 同环境；仍失败就按 `HOST_PRELUDE_FILES` / `HOST_PYTHON` 排查 |
| trace 目录为空 | 启动档位不是 `kernel`；`/start_profile` 超时 | `make up-host LEVEL=kernel`；看 `serve.log` 里 profiler 配置；`WAIT_TRACE` 调大 |
| `watch_steps.sh --docker` 报错 | host 模式没有容器日志 | 用默认文件模式：`make watch` / `scripts/watch_steps.sh --run-dir …` |
| `compare` 出来的差异很大 | 版本/参数/档位/机器状态不同 | 按 §7 的可比性条件逐项核对；重复多次看噪声 |
| `.env` 里设了 `RUNTIME=host`，`make up` 仍按 docker 起 | 命令行/环境显式给了 `RUNTIME=docker` 覆盖了 `.env` | 去掉显式覆盖，或用 `make up-host`；`make -n up` 可看到最终是否注入 RUNTIME |

定位问题时的通用顺序：

```bash
make host-check                    # 环境层
make status-host                   # 进程/端点层
tail -n 100 runs/<ts>/serve.log    # 引擎层
cat runs/<ts>/run_meta.json        # 版本/参数/运行方式
cat runs/<ts>/REPORT.md            # 性能归因层
```

## 10. 可选：systemd 常驻示例

希望把 host 模式做成"开机自启/崩溃重启"的常驻服务时，可以用 systemd 固化环境与限制（示例，按实际路径改）：

```ini
# /etc/systemd/system/vllm-host-probe.service
[Unit]
Description=vLLM host-mode probe instance
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
RemainAfterExit=yes
User=me
WorkingDirectory=/home/me/vllm-docker-probe
Environment=RUNTIME=host
Environment=HOST_PYTHON=/home/me/venv-vllm/bin/python
Environment=HOST_PRELUDE_FILES="DTK_ROOT=/opt/dtk2604 /opt/dtk/env.sh"
# 同机还有其它显存占用/调试时可跳过停止时的显存回落等待（见 §5.2）
# Environment=PROBE_SKIP_VRAM_WAIT=1
# 关键：把环境限制写进 unit（等价于 docker run --ulimit / --shm-size）
LimitMEMLOCK=infinity
LimitSTACK=infinity
LimitNOFILE=65535
# start_vllm.sh 会等 /health 就绪后返回（大模型冷启动可能 5~15 分钟）
ExecStart=/usr/bin/make up-host
ExecStop=/usr/bin/make down-host
TimeoutStartSec=1200
TimeoutStopSec=90
KillMode=process
Restart=no

[Install]
WantedBy=multi-user.target
```

常用操作：

```bash
sudo systemctl daemon-reload
sudo systemctl start vllm-host-probe
journalctl -u vllm-host-probe -f           # start/stop 脚本的输出
systemctl status vllm-host-probe
```

> 说明：`make up-host` 等 `/health` 就绪后**返回**，而 vLLM 是用 setsid 放到后台的（PID 记在 `serve.pid`），
> 所以这里用 `Type=oneshot` + `RemainAfterExit=yes`：systemd 认为服务 "active"，停止时由
> `ExecStop=make down-host` 走优雅停止。这套写法**不会**在 vLLM 崩溃时自动拉起；要自动重启，
> 请把真正的 vLLM 长跑命令（`serve_launch.sh` 的内容）作为 `ExecStart`，或外面再套一层 supervisor，
> 探针侧只负责生成配置与做探测。

## 11. 自测

host 模式的自测脚本不需要 GPU、不需要装 vLLM、甚至不需要 Docker：

```bash
bash tests/host_mode_selftest.sh     # 单独跑
make test                            # 全量测试的第 4 步会跑它
```

它覆盖：临时模型 + 假入口（`python3 -c 'import time;time.sleep(120)'`）启动/停止、
`--dry-run` 输出不含 `docker run`、`serve.pid`/`serve_launch.sh`/`cmd.txt`/`traces` 产物、
`status` 显示「运行方式」、`host_check.sh --json` 产出 JSON（存在时）、
`watch_steps.sh --docker` 在 host 下明确拒绝；
另有公共辅助的单元自测：`prelude` 的 `K=V`/文件 token 解析、`host_exec` 注入环境、
`latest_run_dir` 按目录 mtime 选择最新运行目录。

## 附录：host 模式变量一览

| 变量 | 默认 | 作用 |
|---|---|---|
| `RUNTIME` | `docker` | `docker` / `host` 切换运行方式 |
| `HOST_PYTHON` | `python3` | 本机 Python 解释器 |
| `HOST_SERVE_ENTRYPOINT` | 空 | 自定义启动入口（空=自动拼 `python -m vllm…`） |
| `HOST_PRECHECK` | `1` | 启动前自动预检 |
| `HOST_PRELUDE_FILES` | 空 | 启动前按顺序执行的环境 token（空格分隔；`K=V` → export，文件路径 → 存在则 source；缺文件预检里会提示） |
| `HOST_STOP_TIMEOUT` | `60` | 停止等待秒数（超时 SIGKILL 进程组） |
| `HOST_VLLM_PATTERN` | 见 `.env.example` | host 模式的进程查找/兜底清理正则（`--kill-exec`、`status` 兜底用） |
| `PROBE_SKIP_VRAM_WAIT` | 空 | 设 `1` = stop 时跳过"等显存回落"（等价 `--no-vram-wait`，适合同机还有其它显存占用/假实例调试） |
| `PROBE_LOG_FILE` | 空 | 外部实例日志路径（等价 `probe_all.sh --log-file`；日志会复制为 `<RUN_DIR>/serve.log`，并记入 run_meta 的 `serve_log`） |
| `VLLM_API_KEY` | 空 | 实例带 `--api-key` 时探测需要（请求/端点检查会带 Authorization；探测产物里打码为 `sk-z***310f` 形式；启动类产物按启动命令原样记录） |
| `PYSPY_BIN` | 空（默认 `py-spy`） | py-spy 可执行文件路径 |
