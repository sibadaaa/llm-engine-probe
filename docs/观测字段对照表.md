# 观测字段对照表（vLLM 0.18.x，多厂商）

本文是 [`README.md`](../README.md) 的字段级补充：**每一步能拿到哪些数据、叫什么名字、需要哪个开关**。
大部分内容是跨厂商通用的 vLLM 字段；样例与实测数据来自 Hygon DCU 部署
（`/home/lyh/z100-vllm` 源码 + 现网 `z100-vllm` 实例的日志与 `/metrics`），
厂商专属的差异（SMI 命令、trace 规则包、设备环境变量）见 `vendors/README.md`。

## 1. 观测开关全景（本 fork 支持的全部相关 CLI flag）

| 开关 | 作用 | 产生的数据 | 依赖 |
|---|---|---|---|
| `--enable-logging-iteration-details` | 每个 engine step 打一行明细 | 逐 step 的批次构成/耗时/KV 使用率 | — |
| `--enable-log-requests` | 打印请求级日志（INFO 简版 / DEBUG 详版） | 请求 id、prompt 摘要 | `VLLM_LOGGING_LEVEL` |
| `--max-log-len N` | 截断日志里的 prompt（默认不截断） | 控制日志量 | 配合上面一项 |
| `--enable-per-request-metrics` | 响应体里带逐请求计时 | `metrics.{time_to_first_token_ms, generation_time_ms, queue_time_ms, mean_itl_ms, tokens_per_second}` | 不能与 `--disable-log-stats` 同用 |
| `--enable-prompt-tokens-details` | usage 里带 `prompt_tokens_details.cached_tokens` | 前缀缓存命中 token 数（逐请求） | — |
| `--enable-force-include-usage` | 流式响应强制带 usage（含 `metrics`） | 客户端不必显式传 `stream_options` | — |
| `--per-request-spec-decode-metrics {none,summary,detailed}` | 响应体里带逐请求投机解码指标 | `metrics.speculative_decoding.*`（`detailed` 含逐步数组） | 需启用投机解码；`n==1` |
| `--kv-cache-metrics` | KV block 驻留指标 | `vllm:kv_block_lifetime_seconds` 等 3 个直方图 | 需 log stats 开启 |
| `--kv-cache-metrics-sample R` | 采样率（默认 0.01） | 控制开销 | 配合上一项 |
| `--cudagraph-metrics` | 打印图调度统计表 | 每种 batch 的 padding/replay 次数 | — |
| `--enable-mfu-metrics` | MFU / 读写带宽 | `vllm:estimated_{flops,read_bytes,write_bytes}_per_gpu_total`、日志 `MFU:` 行 | — |
| `--enable-layerwise-nvtx-tracing` | 逐层 NVTX 范围 | trace 中的层/模块范围（含输入输出 shape） | **与 CUDA/HIP Graph 不兼容** |
| `--profiler-config JSON` | 打开 profiler 与 `/start_profile` 端点 | torch trace 文件 | `torch_profiler_dir` 必须绝对路径 |
| `--otlp-traces-endpoint URL` | OTEL 导出目标 | 逐请求 `llm_request` span（`gen_ai.latency.*`、token 用量、`gen_ai.request.id`） | 需要 opentelemetry（镜像内已具备） |
| `--collect-detailed-traces {model,worker,all}` | **本版本实测为空操作**：只做参数校验，`collect_model_forward_time`/`collect_model_execute_time` 无任何消费方，`/metrics` 里也没有 `model_forward_time_milliseconds` | — | 必须同时给 `--otlp-traces-endpoint`；要 forward/execute 细分请改用 torch profiler |
| `--show-hidden-metrics-for-version X.Y` | 重新打开已隐藏的旧指标 | 兼容老看板 | — |
| `--disable-log-stats` | 关闭周期 stats | **会同时关掉** per-request metrics 与 kv-cache metrics | — |

环境变量：

| 变量 | 默认 | 作用 |
|---|---|---|
| `VLLM_LOGGING_LEVEL` | `INFO` | 日志级别（DEBUG 才有请求详版日志） |
| `VLLM_LOG_STATS_INTERVAL` | `10.0` | 周期 stats 间隔（秒）；本站生产用 5 |
| `VLLM_LOG_BATCHSIZE_INTERVAL` | `-1` | 批次大小日志间隔 |
| `VLLM_CUSTOM_SCOPES_FOR_PROFILING` | `0` | 置 1 让引擎内部 `record_function` 范围进入 torch trace（`schedule: *`、`gpu_model_runner: *`、`llm_engine step: *`） |
| `VLLM_NVTX_SCOPES_FOR_PROFILING` | `0` | 同上但用 NVTX 范围（给 rocprof）；与 CUSTOM 是 `if/elif`，**CUSTOM 优先** |
| `VLLM_PROBE_LOG` | `/logs/probe_steps.jsonl` | 本工具箱的 stat logger 插件输出路径 |
| `VLLM_PROBE_DISABLE` | `0` | 置 1 关闭插件（便于 A/B 评估插件自身开销） |
| ⚠️ `VLLM_PLUGINS` | 未设 | **全局插件白名单**。留空=所有插件都加载；一旦设置，vLLM 自带的 `vllm.general_plugins`（LoRA resolver 等）就不再加载。**本工具箱不会设置它** |
| `PROMETHEUS_DISABLE_CREATED_SERIES` | 未设 | 置 1 可去掉 `*_created` 序列，抓取体积约 -20% |

`--profiler-config` 的字段（`vllm/config/profiler.py`）：

```json
{
  "profiler": "torch",
  "torch_profiler_dir": "/traces",
  "torch_profiler_with_stack": true,
  "torch_profiler_with_flops": true,
  "torch_profiler_record_shapes": true,
  "torch_profiler_with_memory": true,
  "torch_profiler_dump_cuda_time_total": true,
  "torch_profiler_use_gzip": true,
  "capture_torch_profiler": false,
  "detailed_trace_annotation": false
}
```

> `detailed_trace_annotation: true` 会给 trace 注解加上 roofline 指标（sk/sqsq/sqsk）；
> 默认 `false` 时注解只带 context/generation 请求数与 token 数（就是本工具箱用来做
> 「预填充 step vs 解码 step」归因的那个名字）。

## 3. `/metrics` 指标（实测 104 个族 / 577 条序列）

标签约定：`{engine="0", model_name="qwen3.8-27b"}`；直方图另有 `le`。

### 3.1 按推理阶段

| 阶段 | 指标 | 类型 | 说明 |
|---|---|---|---|
| 排队 | `vllm:request_queue_time_seconds` | histogram | WAITING 阶段（**本部署桶从 0.3s 起步，分辨率差**） |
| 排队 | `vllm:num_requests_waiting` / `_by_reason{reason=capacity\|deferred}` | gauge | 等待请求数与原因分解 |
| 预填充 | `vllm:request_prefill_time_seconds` | histogram | PREFILL 阶段 |
| 预填充 | `vllm:request_prefill_kv_computed_tokens` | histogram | 本次真正新算的 KV token（不含命中缓存的） |
| 预填充 | `vllm:prompt_tokens_total` / `vllm:prompt_tokens_by_source` | counter | 预填充 token 数 / 来源分解 |
| 解码 | `vllm:request_decode_time_seconds` | histogram | DECODE 阶段 |
| 解码 | `vllm:request_time_per_output_token_seconds` | histogram | 逐请求 TPOT |
| 解码 | `vllm:inter_token_latency_seconds` | histogram | 相邻输出 token 间隔（ITL） |
| 解码 | `vllm:generation_tokens_total` | counter | 生成 token 数 |
| 运行合计 | `vllm:request_inference_time_seconds` | histogram | RUNNING = prefill + decode |
| 端到端 | `vllm:e2e_request_latency_seconds` | histogram | 请求进入引擎到结束 |
| 首 token | `vllm:time_to_first_token_seconds` | histogram | TTFT |
| 引擎 step | `vllm:iteration_tokens_total` | histogram | 每个 engine step 处理的 token 数 |
| 请求形状 | `vllm:request_prompt_tokens`、`request_generation_tokens`、`request_max_num_generation_tokens`、`request_params_n`、`request_params_max_tokens` | histogram | 负载画像 |
| 结果 | `vllm:request_success_total{finished_reason}` | counter | 完成原因（stop / length / abort） |
| 抢占 | `vllm:num_preemptions_total`、`vllm:request_num_preemptions` | counter/histogram | 被抢占次数 |

### 3.2 缓存 / 显存

| 指标 | 类型 | 需要开关 | 说明 |
|---|---|---|---|
| `vllm:kv_cache_usage_perc` | gauge | — | KV 使用率（1.0 = 100%） |
| ~~`vllm:cpu_cache_usage_perc`~~、~~`vllm:gpu_cache_usage_perc`~~、~~`vllm:num_requests_swapped`~~ | — | — | **本版本已不存在**（实测 104 个指标族中均无；旧版 vLLM 的 CPU 交换区/GPU 缓存命名，已分别被 KV offloading 与 `kv_cache_usage_perc` 取代）。老看板/老脚本引用它们会静默拿到空序列 |
| `vllm:cache_config_info{...}` | gauge=1 | — | 缓存配置快照（`block_size`、`kv_cache_size_tokens`、`enable_prefix_caching`、`num_gpu_blocks` …） |
| `vllm:prefix_cache_queries_total` / `_hits_total` | counter | 前缀缓存开 | 命中率 = hits/queries |
| `vllm:prompt_tokens_cached_total` | counter | — | 命中缓存的 prompt token 数 |
| `vllm:external_prefix_cache_*`、`vllm:mm_cache_*` | counter | 对应功能开 | 跨实例前缀缓存 / 多模态缓存 |
| `vllm:kv_block_lifetime_seconds` | histogram | `--kv-cache-metrics` | block 从分配到驱逐 |
| `vllm:kv_block_idle_before_evict_seconds` | histogram | 同上 | 驱逐前空闲时长 |
| `vllm:kv_block_reuse_gap_seconds` | histogram | 同上 | 相邻两次访问间隔（复用局部性） |

### 3.3 投机解码 / 算力

| 指标 | 说明 |
|---|---|
| `vllm:spec_decode_num_drafts_total` | 验证步数 |
| `vllm:spec_decode_num_draft_tokens_total` / `_num_accepted_tokens_total` | 草稿数 / 接受数 |
| `vllm:spec_decode_num_accepted_tokens_per_pos_total{position}` | 每个草稿位置的接受数（诊断 k 是否过大） |
| `vllm:estimated_flops_per_gpu_total` | `--enable-mfu-metrics`；配合时间算 TF/s per GPU |
| `vllm:estimated_read_bytes_per_gpu_total`、`..._write_bytes_...` | 同上；判断是否访存受限 |
| `vllm:engine_sleep_state` | 睡眠模式状态 |
| `vllm:tool_call_parser_invocations_total` | 工具解析器调用（懒注册） |
| `http_request_duration_highr_seconds` | API server 侧 HTTP 延迟（22 桶，无标签，适合算分位） |

### 3b. Strata 引擎上的 `/metrics` 对照（`ENGINE=strata`）

> 来源：[`design/strata-engine/事实核对.md`](design/strata-engine/事实核对.md) §6（⭐ 以真机核对为准）。
> 抓取注意：`GET /metrics` **默认返回 JSON**，探针已自动追加 `?format=prometheus`
> （profile 字段 `ENGINE_METRICS_FETCH_SUFFIX`）；手动抓取需带该参数或 `Accept: text/plain`。

**vLLM 同名子集**（`metrics.vllm-named` 能力；`probe metrics` 解析层直接复用）：

| 指标 | 类型 | 说明 |
|---|---|---|
| `vllm:num_requests_running` / `vllm:num_requests_waiting` | gauge | 就绪轮询正则即取这两个（无 `cache_config_info`） |
| token 与 request 计数器 | counter | prompt/generation/success 等同名族 |
| `vllm:prefix_cache_queries_total` / `_hits_total` | counter | 前缀缓存命中 |
| `vllm:spec_decode_num_draft_tokens_total` / `_num_accepted_tokens_total` | counter | MTP 投机解码（per-position 分布**无**） |
| `vllm:kv_cache_usage_perc` | gauge | KV 使用率 |
| `vllm:time_to_first_token_seconds` / `vllm:inter_token_latency_seconds` / `vllm:e2e_request_latency_seconds` | histogram | TTFT / ITL / e2e |

**缺失的 vLLM 指标**（探针按缺项容错，报告显示 `available=False`，属预期）：
`vllm:request_queue_time_seconds` / `request_prefill_time_seconds` / `request_decode_time_seconds` /
`request_inference_time_seconds` / `request_time_per_output_token_seconds`（5 个生命周期直方图）、
`vllm:cache_config_info`（就绪轮询默认正则匹配不到，引擎 profile 已换计数器）、
`vllm:kv_block_*` 系、`vllm:num_preemptions_total`、per-request spec 分布。

**`strata:` 专有指标**（F3 的可选采集面 `--engine-extras`；缺失值不出样本，不是 0）：

> 采集条件：`probe metrics --engine-extras`（或 `PROBE_ENGINE_EXTRAS=1`）显式开启后，
> 按 profile 的 `extra_metric_families` 前缀（`strata:live_` / `strata:last_` / `strata:totals_` /
> `strata:gpu_` / `strata:ram_` / `strata:cpu` / `strata:engine_`）采集，落快照 JSON 的
> `meta.engine_extra` 段并在 TSV 末尾追加行；默认关闭时产物 schema 不变。
> 抓取鉴权与 OpenAI 端点同（Bearer）。

| 前缀 / 指标 | 说明 |
|---|---|
| `strata:live_state{state}` / `strata:live_tok_s` / `strata:live_prefill_tok_s_mean` / `strata:live_prompt_read` | 实时状态与速率 |
| `strata:engine_max_context` | 当前上下文上限 |
| `strata:totals_prompt_seconds_total` / `strata:totals_decode_seconds_total` | 累计耗时 |
| `strata:last_hit_rate` / `strata:last_decode_tok_s` | 专家缓存命中率 / 最近 decode 速率 |
| `strata:gpu_util` / `strata:gpu_mem_used_bytes` / `strata:gpu_mem_total_bytes` / `strata:gpu_temp_celsius` / `strata:gpu_power_watts{gpu}` | 硬件面（可作遥测旁路；SMI 面仍按 VENDOR 走） |
| `strata:cpu` / `strata:ram_used_bytes` / `strata:ram_total_bytes` | CPU / 内存 |

### 3c. SGLang 引擎上的 `/metrics` 对照（`ENGINE=sglang`）

> 来源：docs.sglang.io《Production Metrics》与上游 `metrics_collector.py`（2026-10 核对，
> ⭐ 以真机核对为准）。抓取注意：**必须启动 flag `--enable-metrics`（默认关）**，否则
> `/metrics` 基本为空；plain GET 即返回 Prometheus 文本（无需查询串）；主标签 `model_name`。

**核心指标**（prometheus 形态；探针按 `metric_prefix="sglang:"` 过滤）：

| 指标 | 类型 | 说明 |
|---|---|---|
| `sglang:num_running_reqs` / `sglang:num_queue_reqs` | gauge | 就绪轮询正则取 `num_running_reqs`（注意是复数，与 vLLM 的 `num_requests_running` 不同名） |
| `sglang:time_to_first_token_seconds` / `sglang:inter_token_latency_seconds` / `sglang:e2e_request_latency_seconds` / `sglang:request_time_per_output_token_seconds` | histogram | TTFT / ITL / e2e / TPOT |
| `sglang:prompt_tokens_total` / `sglang:generation_tokens_total` | counter | token 吞吐分子 |
| `sglang:gen_throughput` / `sglang:cache_hit_rate` / `sglang:token_usage` / `sglang:num_used_tokens` | gauge | 生成吞吐 / radix 缓存命中 / KV token 使用 |
| `sglang:is_cuda_graph` / `sglang:cuda_graph_passes_total` | gauge/counter | 图模式观测（报告图模式小节暂未接入，属后续增强） |
| `sglang:spec_accept_length` / `sglang:spec_accept_rate` / `sglang:spec_cap_length` / `sglang:spec_num_steps` / `sglang:spec_num_draft_tokens` | gauge | 投机解码（EAGLE/NEXTN/NGRAM 启用时出现） |

**与 vLLM 的差异**：无 `vllm:cache_config_info`（就绪正则已换 `num_running_reqs`）；
无逐请求 metrics 响应字段（`obs.per-request-metrics` 未声明，报告"逐请求指标"小节为空属预期）；
dp_attention 场景指标默认挂 TP0（分 rank 需 `--enable-metrics-for-all-schedulers`）。

### 3e. Ollama（`ENGINE=ollama`）：无指标面

> 截至 v0.40.8（2026-10 核对）主线**无 `/metrics` 端点**（上游指标 PR #16998/#18508
> 尚未合并）。`metrics_flavor=none`：探针跳过指标抓取与就绪指标轮询，就绪判定走
> `GET /`（200 "Ollama is running"）；报告无服务端指标小节、时延/吞吐均为客户端口径。
> 请求级 usage（prompt_tokens/completion_tokens）与 Ollama 扩展 `timings` 在响应体内，
> 需要时按响应 JSON 自行提取。上游合并指标 PR 后按 prometheus flavor 回填本节。

## 4. 日志行格式（可直接写正则）

来源：`vllm/v1/metrics/loggers.py`、`vllm/v1/spec_decode/metrics.py`、`vllm/v1/metrics/perf.py`、
`vllm/compilation/cuda_graph.py`。实测样例在 [`samples/serve.log`](../samples/serve.log)。

**① 逐 iteration 明细**（`--enable-logging-iteration-details`）

```
Engine 000: Iteration(752): 0 context requests, 0 context tokens, 1 generation requests,
8 generation tokens, iteration elapsed time: 184.79 ms, GPU KV cache usage: 3.5%
```

可选字段：`encoder inputs: N, encoder output embeddings: M`（多模态/编码器场景，插在 `ms` 之后）。
`ctx_tokens>0 && gen_tokens==0` ⇒ 纯预填充 step；`ctx>0 && gen>0` ⇒ 混合 step（chunked prefill）；
两者都为 0 ⇒ 空转 step。

**② 周期 stats**（默认开启，间隔 = `VLLM_LOG_STATS_INTERVAL`）

```
Engine 000: Avg prompt throughput: 0.0 tokens/s, Avg generation throughput: 8.0 tokens/s,
Running: 0 reqs, Waiting: 0 reqs, GPU KV cache usage: 0.0%, Prefix cache hit rate: 27.0%
```

可能追加：`External prefix cache hit rate: X%`、`MM cache hit rate: X%`、`Corrupted: N reqs`。

**③ 投机解码**（统计间隔打印）

```
SpecDecoding metrics: Mean acceptance length: 1.69, Accepted throughput: 3.34 tokens/s,
Drafted throughput: 33.73 tokens/s, Accepted: 18 tokens, Drafted: 182 tokens,
Per-position acceptance rate: 0.462, 0.115, 0.077, 0.038, 0.000, 0.000, 0.000,
Avg Draft acceptance rate: 9.9%
```

**④ MFU**（`--enable-mfu-metrics`）

```
Engine 000: MFU: 0.6 TF/s/device 32.4 GB/s/device
```

**⑤ 图调度统计**（`--cudagraph-metrics`，Markdown 表格）

```
**CUDAGraph Config Settings:**
- Mode: NONE
- Capture sizes: []
**CUDAGraph Stats:**
| Unpadded Tokens | Padded Tokens | Num Paddings | Runtime Mode | Count |
|-----------------|---------------|--------------|--------------|-------|
```

## 5. torch profiler trace（Chrome Trace JSON）

文件命名：`rank<N>.<纳秒时间戳>.pt.trace.json[.gz]`，写在 `--profiler-config` 的
`torch_profiler_dir` 下；torch 还会额外写 `profiler_out_<rank>.txt`（key-averages 表，已被本工具箱解析）。

事件结构（每条）：

```json
{"ph": "X", "cat": "kernel", "name": "fp8_emu_gemm_block_kernel<...>",
 "pid": 0, "tid": 20, "ts": 123456, "dur": 1261, "args": {"device": 0, "stream": 7}}
```

| 字段 | 判定 | 含义 |
|---|---|---|
| `pid == 0` | 设备侧事件 | GPU 上真实执行的 kernel / 注解 |
| `pid != 0` | CPU 侧事件 | Python/ATen/运行时调用（含同步等待） |
| `cat == "kernel"` | **叶子 GPU 事件** | 真实 kernel 执行时间（占比的分母） |
| `cat == "gpu_user_annotation"` | **区间型 GPU 事件** | NVTX/注释范围，**包含**其内部 kernel，不能与叶子相加 |
| `cat == "user_annotation"` | CPU 侧范围 | `ProfilerStep#N`、`execute_context_*` 等 |
| `cat == "cpu_op"` / `"cuda_runtime"` | CPU 侧 | 算子调用 / 运行时（launch、同步） |
| `cat == "memory"` | 内存事件 | 需要 `torch_profiler_with_memory` |

分类规则（`probe/trace_probe.py::CATEGORY_RULES`，可自行扩充）：
通信/集合通信 → MoE → 量化/GEMM → Attention → GDN/Mamba → Norm/激活 → 采样/logits →
KV/搬运 → 图/框架 → 其它。

关键派生量：

| 派生量 | 算法 | 用途 |
|---|---|---|
| GPU busy | 叶子区间并集长度 | 真实忙碌时间 |
| GPU 利用率 | GPU busy / 时间窗 | 是否有空洞（CPU 瓶颈/同步等待） |
| 分类占比 | 分类 GPU 时间 / 叶子总时间 | 定位主瓶颈（GEMM？通信？Attention？） |
| 逐 step wall/GPU | `ProfilerStep#N` 区间与并集求交 | step 级 CPU/GPU 对照 |
| 预填充/解码归因 | `execute_context_A(B)_generation_C(D)` 注解 | 直接把 GPU 时间拆成两类 step，并算每 token 成本 |

## 5b. stat logger 插件（引擎内部结构化数据）

这是本工具箱**最深、最精确**的一层：不解析文本、不抓指标，直接在引擎进程内把
`SchedulerStats` / `IterationStats` 落成 JSONL。

* 插件组（entry point）：`vllm.stat_logger_plugins`（`vllm/plugins/__init__.py::STAT_LOGGER_PLUGINS_GROUP`）
* 基类：`vllm.v1.metrics.loggers.StatLoggerBase`；entry point 的值必须是**类**（子类），
  否则 `load_stat_logger_plugin_factories()` 抛 `TypeError`
* 构造：每个 engine 一个实例，`factory(vllm_config, engine_index)`（两个**位置参数**）
* 回调：`record(scheduler_stats, iteration_stats, mm_cache_stats=None, engine_idx=0)`，每个 engine step 一次
* 可选实现：`log()`、`record_sleep_state(is_awake, level)`、必须实现 `log_engine_initialized()`
* vLLM 官方声明：`SchedulerStats` / `IterationStats` **不是稳定接口**，字段可能变 →
  本插件全部用 `getattr` 取值，缺失字段只丢该项（并有"与版本字段一致性"自检）

记录结构（`plugin_probe/vllm_probe_stat_logger/records.py::build_record`）：

| JSON 字段 | 来源类（本机 0.18.1+das 实测字段名） |
|---|---|
| `iter` | `SchedulerIterationDetails`: iteration_index, num_ctx_requests, num_ctx_tokens, num_generation_requests, num_generation_tokens, elapsed_ms, num_encoder_inputs, num_encoder_output_tokens, is_dummy |
| `sched` | `SchedulerStats`: num_running_reqs, num_waiting_reqs, num_skipped_waiting_reqs, kv_cache_usage, step_counter, current_wave, waiting/running_lora_adapters |
| `prefix` / `connector_prefix` | `PrefixCacheStats`: requests, queries, hits, preempted_requests, preempted_queries, preempted_hits |
| `spec` | `SpecDecodingStats`: num_spec_tokens, num_drafts, num_draft_tokens, num_accepted_tokens, **num_accepted_tokens_per_pos**, num_draft_tokens_per_pos（另派生接受率与平均接受长度） |
| `evict` | `KVCacheEvictionEvent`: lifetime_seconds, idle_seconds, reuse_gaps_seconds |
| `graph` | `CUDAGraphStat`: num_unpadded_tokens, num_padded_tokens, num_paddings, runtime_mode |
| `perf` | `PerfStats`: num_flops_per_gpu, num_read_bytes_per_gpu, num_write_bytes_per_gpu |
| `prompt_tokens` | `PromptTokenStats`: computed, local_cache_hit, external_kv_transfer, cached_tokens, total |
| `reqs` | `FinishedRequestStats`: request_id, finish_reason, num_prompt_tokens, num_cached_tokens, num_generation_tokens, num_preemptions, queued_time, prefill_time, decode_time, inference_time, e2e_latency, mean_time_per_output_token, max_tokens_param, is_corrupted |
| `samples` | `IterationStats`: time_to_first_tokens_iter, inter_token_latencies_iter, num_generation_tokens, num_preempted_reqs, max_num_generation_tokens_iter, num_corrupted_reqs（数组截断到 256） |

门控与边界：

* `iter` 需要 `--enable-logging-iteration-details`（引擎侧 `capture_iteration_details` 同时要求
  log stats 开启），其余分组不受档位影响。
* 每条记录写一行并 flush；逐步数组与逐请求明细都有上限（256 / 512），避免高并发下膨胀。
* 插件异常全部被吞掉并累计到 `failures`，**不影响推理**。

## 6. 逐请求 `metrics` 响应字段（`--enable-per-request-metrics`）

```json
{
  "usage": {"prompt_tokens": 42, "completion_tokens": 128,
            "prompt_tokens_details": {"cached_tokens": 4096}},
  "metrics": {
    "time_to_first_token_ms": 85.2,
    "generation_time_ms": 1240.5,
    "queue_time_ms": 12.3,
    "mean_itl_ms": 9.1,
    "tokens_per_second": 103.2,
    "speculative_decoding": {
      "mean_acceptance_length": 1.2325,
      "draft_acceptance_rate": 0.0775,
      "acceptance_histogram": [39, 1, 0, 3],
      "num_spec_steps": 43,
      "num_accepted_draft_tokens": 10,
      "num_draft_tokens": 129,
      "num_spec_tokens": 3,
      "per_step_accepted": [2, 0, 1, 3],
      "per_step_drafted": [3, 3, 3, 3]
    }
  }
}
```

约束（源码行为，务必记住）：

* 只在 `n == 1` 时返回；`n > 1` 时 `metrics` 为 `null`（计时无法归因到单条序列）。
* 流式响应挂在**最后一个 usage chunk** 上，需要 `stream_options.include_usage=true`
  或服务端 `--enable-force-include-usage`（本工具箱默认两者都保证）。
* `speculative_decoding` 需要 `--per-request-spec-decode-metrics summary|detailed`，
  且 `n == 1`、启用了投机解码；该字段官方标注为实验性。
* 逐请求字段与聚合计数器的对账关系：
  `Σnum_spec_steps = vllm:spec_decode_num_drafts_total`、
  `Σnum_draft_tokens = vllm:spec_decode_num_draft_tokens_total`、
  `Σnum_accepted_draft_tokens = vllm:spec_decode_num_accepted_tokens_total`。
