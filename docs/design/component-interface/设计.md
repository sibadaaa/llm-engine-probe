## 1. 目标与非目标

### 目标

1. 把"被探测的引擎是谁"从硬编码假设变成**注册表 + 能力位（caps）**：
   shell 端 `engines/<id>.sh`、Python 端 `probe/engines.py`，两端键集合由测试强制一致
   （复刻 `vendors/` ↔ `probe/vendors.py` 的双端模式，见 `tests/test_vendors.py`）。
2. `scripts/start_vllm.sh` 的 vLLM 专属块（观测档位 flag、投机解码、NVTX、插件、
   `VLLM_*` 环境等）按能力位收拢；**文件里不出现新的 `ENGINE == "<id>"` 字符串比较**。
3. 新引擎接入 = 新增 profile + 模板 + 两行索引（见 design/README.md §4），不改既有分支。
4. `ENGINE=vllm`（默认、不设置）路径行为逐字节不变（design/README.md §5 红线 1）。
5. 探针面（`probe/config.py` / `hostcheck` / `report` / `metrics` / `trace` / `status.sh`）
   获得"引擎身份 + 能力"的一致来源；能力缺失时的降级是**显式、有文案的**，不是静默。

### 非目标（本期明确不做）

* docker 模式的引擎支持（`docker/` 不动；非 vLLM 引擎在 `RUNTIME=docker` 下显式报错）；
* DeepEP 等**增强型组件**的抽象（它们不替换服务进程，继续走 `hosts/<类目>/*.env` 模板）；
* 把 DeepInfer/DeepEP 真正注册进来（那是《../施工图-DeepSeek部署栈支持.md》的事，本期只留
  迁移路径说明）；Strata 的落地在 F2（`strata-engine/`）；
* `vendors/` 厂商层的任何改动（引擎与厂商正交：Strata 也跑在 nvidia/amd/intel 上，
  遥测/trace 归因继续按厂商走）。

## 2. 概念模型

```
                 ┌────────────────────────────────────────────────┐
                 │  hosts/ 模板层（部署形态：只写 KEY=VALUE 的叠加） │
                 │  vendor/ scenario/ quant/ spec/ deploy/ engine/ │
                 └───────────────────────┬────────────────────────┘
                                         │ 模板链叠加 + .env + 显式环境
                                         ▼
   ENGINE=... ──> engines/<id>.sh ──> scripts/start_vllm.sh（按 caps 收拢的启动链）
                     │                     │
                     │ 双端一致性守卫        ▼
                     │               serve_launch.sh（host launcher）
                     ▼
              probe/engines.py ──> probe/config.py（engine 字段落产物）
                     │                │
                     │                ├── probe/hostcheck.py（引擎预检，按 caps）
                     │                ├── probe/metrics_probe.py（按 metrics flavor）
                     │                ├── probe/http_probe.py（协议面，基本引擎无关）
                     │                ├── probe/report.py（引擎行 + 能力降级注记）
                     │                └── probe/trace_probe.py（kernel 档按 caps 门禁）
                     ▼
              tests/test_engines.py（shell↔Python 注册表一致性）
```

三个维度的边界：

| 概念 | 判定标准 | 例子 | 接入位置 |
|---|---|---|---|
| **引擎组件** | 提供服务进程、替换 serve 入口 | vLLM、Strata、DeepInfer | `engines/<id>.sh` + `hosts/engine/<id>.env` |
| **增强型组件** | 不替换进程，只追加 flag/env | DeepEP、投机解码、量化 | `hosts/<类目>/*.env`（现状即可） |
| **硬件厂商** | GPU/NPU 硬件维度 | nvidia、hygon、ascend | `vendors/<id>.sh`（不动） |

## 3. 能力枚举（caps 词表）——契约核心

能力键是**封闭词表**：`<域>.<项>` 小写连字符格式，两端注册表只能使用下表中的键；
`tests/test_engines.py` 校验所有声明的 caps ∈ 词表（防拼写错误静默生效）。

| 能力键 | 语义 | 缺失时的探针行为 |
|---|---|---|
| `api.openai-chat` | 提供 `POST /v1/chat/completions` | 缺失 → http 探测拒绝启动并指明原因 |
| `api.openai-completions` | 提供 `POST /v1/completions` | 缺失 → `PROBE_ENDPOINT=completions` 报错 |
| `api.models-list` | 提供 `GET /v1/models` | 缺失 → status/预检跳过模型列表核对并注记 |
| `api.health` | 提供 `GET /health`（或 `health_path` 指定路径） | 缺失 → 就绪等待退化为端口连通性探测 |
| `api.props` | 提供 `GET /props` 元数据端点 | 缺失 → 不采集引擎元数据 |
| `metrics.vllm-named` | `/metrics` 以 vLLM 指标名输出 Prometheus 文本 | 有 → metrics 探针按现有逻辑直接复用 |
| `metrics.prometheus` | `/metrics` 有 Prometheus 文本但**非** vLLM 命名 | 仅此无前者 → 按通用白名单采集（F3） |
| `obs.step-log` | 引擎支持逐 step 日志观测（vLLM `PROBE_LEVEL=steps` 依赖项） | 缺失 → `PROBE_LEVEL∈{steps,deep,kernel}` 降级为 `basic` + ⚠️ 文案 |
| `obs.per-request-metrics` | 支持逐请求 metrics 字段（vLLM `--enable-per-request-metrics`） | 缺失 → `deep` 档相关 flag 不拼装 |
| `obs.spec-metrics` | 投机解码逐请求指标可观测 | 缺失 → `SPEC_DECODE_ON=0` 同语义 |
| `obs.trace-pytorch` | 支持 torch profiler kernel trace | 缺失 → kernel 档拒绝并提示（不生成空 trace） |
| `obs.graph-mode` | 有图模式（CUDA Graph 等）统计可归因 | 缺失 → 报告图模式小节注明"本引擎不适用" |
| `spec.decode` | 引擎自带投机解码配置面 | 缺失 → `DRAFT_MODEL/SPEC_*` 非空时 die |
| `runtime.docker` | 有官方/可用镜像 | 缺失 → `RUNTIME=docker` 下 die（文案含暂缓说明） |
| `runtime.host` | 支持物理机拉起 | 缺失 → host 启动链拒绝 |

> 设计纪律：新增能力键必须同时更新本文表格、两端注册表词表与 `tests/test_engines.py`
> 的 `CAP_VOCAB`，三个位置一致才允许合入。

## 4. shell 端契约：`engines/<id>.sh`

文件位置与命名：`engines/<id>.sh`，`<id>` 即 `ENGINE` 的取值（小写字母数字连字符）。
`engines/_template.sh` 为骨架（仿 `hosts/_template.env` 的注释规范）。

source 无副作用（子 shell 干净环境 `PATH=""` 下 `source` 必须成功）——与 `vendors/*.sh`
同一纪律（`tests/test_vendors.py::test_profiles_are_side_effect_free` 同款测试复刻）。

### 4.1 字段规范

| 变量 | 必填 | 语义 | 默认（vllm） |
|---|---|---|---|
| `ENGINE_ID` | ✅ | 必须与文件名一致 | `vllm` |
| `ENGINE_LABEL` | ✅ | 报告/CLI 展示名 | `vLLM` |
| `ENGINE_ENTRYPOINT` | ✅ | host 模式默认 serve 入口命令（会被 `HOST_SERVE_ENTRYPOINT` 覆盖） | 空（走现有 `host_serve_entrypoint()` 的 vLLM 默认） |
| `ENGINE_PROCESS_PATTERN` | ✅ | stop/status 的进程查找正则（可被 `HOST_ENGINE_PATTERN` 覆盖） | 空（回落 `HOST_VLLM_PATTERN`） |
| `ENGINE_HEALTH_PATH` | — | 就绪探测路径 | `/health` |
| `ENGINE_MODELS_PATH` | — | 模型列表路径 | `/v1/models` |
| `ENGINE_METRICS_FLAVOR` | ✅ | `vllm-named` \| `prometheus` \| `none` | `vllm-named` |
| `ENGINE_ARGS_MODE` | ✅ | 参数拼装模式：`vllm-cli`（走 `start_vllm.sh` 现有 vLLM flag 拼装）\| `custom`（跳过全部 vLLM flag 块，只用 `EXTRA_ENGINE_ARGS`/`EXTRA_ARGS_FILE`） | `vllm-cli` |
| `ENGINE_READY_METRIC` | — | 就绪等待轮询 `/metrics` 的正则；空 → 回落厂商默认（`VENDOR_READY_METRIC`，`common.sh:188` 现值 `^vllm:cache_config_info`） | 空 |
| `ENGINE_METRICS_FETCH_SUFFIX` | — | 抓 `/metrics` 时追加的查询串（如 `?format=prometheus`），用于"默认返回 JSON、需显式要 Prometheus 文本"的引擎（Strata）；`start_vllm.sh` 就绪轮询与探针抓取共用 | 空 |
| `ENGINE_CAPS` | ✅ | 能力键列表（空格分隔） | 见 §3 词表中 vllm 的全集（除特别注明的例外） |
| `ENGINE_VERSION_CMD` | — | hostcheck 版本探测命令（无则用 HTTP 元数据） | 空 |
| `ENGINE_CHECK_SEVERITY` | ✅ | 引擎预检缺失时的处置：`warn` \| `fail` | vllm=`fail`；新引擎建议 `warn`（外部探测模式常见） |
| `ENGINE_DOCKER_IMAGE` | — | 镜像引用；空 = 无 docker 支持 | 空（vllm 的镜像选择走现有 `IMAGE` 流程，此字段留空不参与） |
| `ENGINE_NOTES` | — | 一句话备注（进 `probe engine` 输出） | 空 |

### 4.2 加载函数（`scripts/lib/common.sh` 新增）

```bash
# 语义：解析 ENGINE 并加载 profile（仿现有 vendor_meta 的子 shell source 法）
engine_meta          # 设定 ENGINE_ID/ENGINE_LABEL/ENGINE_CAPS/... 全部 ENGINE_* 变量
                     # （2026-10-22 评审修订：加载期校验 ENGINE_LABEL/ENGINE_CAPS/
                     #  ENGINE_METRICS_FLAVOR/ENGINE_ARGS_MODE 必填，缺失即 die）
engine_has_cap <key> # $ENGINE_CAPS 里按词匹配，返回 0/1
                     # （2026-10-22 评审修订：实现用"按空白拆行 + 整行精确比对"，
                     #  不用 grep -qw——能力键含 '.'/'-'，-qw 的词边界会把 "obs.step"
                     #  误判成 "obs.step-log" 的词；tests/test_engines.py 有专项断言）
engine_list          # 列出 engines/*.sh 的 id（engines_list 命令用）
```

加载时机：`start_vllm.sh` 读入配置后立即 `engine_meta`，随后做合法性检查
（`ENGINE` 未知 → die；`RUNTIME=docker` 且无 `runtime.docker` → die）。
`ENGines` 相关变量全部进 `common.sh` 末尾的 export 列表（`serve_launch.sh` 才能带上）。

### 4.3 配置键（新增，三处同步）

| 键 | 默认 | 说明 |
|---|---|---|
| `ENGINE` | `vllm` | 引擎组件 id；进 `.env.example`（新小节「0b. 引擎组件」）+ `common.sh` 的 `: "${ENGINE:=vllm}"` |
| `EXTRA_ENGINE_ARGS` | 空 | **引擎无关**的追加参数键（末尾追加，语义同 `EXTRA_VLLM_ARGS`）；对 vLLM 与 `EXTRA_VLLM_ARGS` 等效合并 |
| `HOST_ENGINE_PATTERN` | 空 | 显式覆盖进程正则；优先级 显式环境 > 模板 > `ENGINE_PROCESS_PATTERN` > `HOST_VLLM_PATTERN`（旧键保留兼容，`.env.example` 注明语义变化） |

`EXTRA_VLLM_ARGS` 的跨引擎语义（**防静默错配**）：`ENGINE != vllm` 时该键被忽略且启动链打
⚠️（键名含 vllm，误用大概率是模板叠错）；要用追加参数请改 `EXTRA_ENGINE_ARGS`。
`EXTRA_ENV` 本来就是引擎无关键，两引擎通用，语义不变。

## 6. 双端一致性守卫：`tests/test_engines.py`

复刻 `tests/test_vendors.py` 的模式（该文件就是模板，照抄结构换对象）：

1. 文件集合一致：`engines/*.sh`（排除 `_` 开头）的 stem 集合 == `ENGINE_REGISTRY` 键集合；
2. 每个 profile 的 `ENGINE_ID` 与文件名一致、`ENGINE_LABEL` 非空；
3. `ENGINE_METRICS_FLAVOR` 两端一致；`ENGINE_CAPS` 两端**集合相等**（顺序无关）；
4. 所有 caps ∈ `CAP_VOCAB`（词表与本文 §3 同步维护在测试里）；
5. 无副作用：`PATH=""` 的干净子 shell `source` 每个 profile 必须成功；
6. `resolve_engine` 优先级：显式参数 > `ENGINE` 环境变量 > `vllm`；未知 id 抛 `KeyError`；
7. shell 端 `engine_has_cap` 的词匹配行为（真实子 shell 验证）。

## 7. 启动链收拢原则（`scripts/start_vllm.sh`）

收拢不是重写。规则：

1. 引擎合法性检查紧跟配置读入（`engine_meta` 之后）：未知 `ENGINE` die；非 vLLM 且
   `RUNTIME=docker` die（除非 profile 有 `runtime.docker`）；`DRAFT_MODEL/SPEC_*` 非空且
   无 `spec.decode` die；`PROBE_LEVEL` 需要 `obs.step-log` 而不得 → 降级 `basic` + ⚠️。
2. vLLM 专属块逐一改为 caps 门禁（`if engine_has_cap obs.step-log; then ...` 等价改写），
   块的内容不改；`ENGINE=vllm` 的拼装结果必须与改写前逐字节一致（用 dry-run 基线 diff 验收）。
3. 入口段：`HOST_SERVE_ENTRYPOINT` 非空 → 用之；否则 `ENGINE_ENTRYPOINT` 非空 → 用之；
   否则现有 vLLM 默认。优先级在 `.env.example` 与 `hosts/README.md` 同步注明。
4. stop/status：进程正则按 §4.3 的 `HOST_ENGINE_PATTERN` 优先级链取值。
5. `run_meta.json` 的 meta 增加 `"engine"`；`serve_launch.sh` 头注释打印引擎与能力位
   （便于事后核对产物归属）。

## 8. hostcheck 契约（`probe/hostcheck.py`）

新增 `_check_engine`（仿 `_check_vllm` 的注册模式进 `_CHECKS`，位于 `vllm` 检查项之前）：

* `ENGINE_VERSION_CMD` 非空 → 在 host 侧执行该命令取版本；命令不存在/失败按
  `ENGINE_CHECK_SEVERITY` 处置（warn 不 fail / fail）；
* `ENGINE_VERSION_CMD` 为空 → 尝试 `GET /props`（有 `api.props` cap）或 skip；
* 引擎= vllm 时保持现有行为不变（`_check_vllm` 不动）；
* 版本字段透传链（`collect_hostcheck` → 内嵌 Python 脚本 → 结果 JSON 的白名单）按
  现有 `deep_ep` 检查项同款方式补 `engine_version`；
* 结果 JSON 顶层增加 `"engine"` 与 `"engine_caps"`。

## 9. 模板层契约：`hosts/engine/` 类目

* 新类目目录 `hosts/engine/`，骨架与编写规范同 `hosts/_template.env`
  （无副作用、键名白名单、文件头三行"用途/适用/组合"）。
* **链序约定**：`vendor/ → scenario/ → quant|spec（vLLM 专属）→ engine/（最后）`。
  引擎模板负责把模型/并行参数换成该引擎的语义（如 Strata 的模型是 pack 名不是文件路径），
  因此放在最后覆盖。
* `hosts/lib/env_overlay.sh` 的 `host_template_show()` 展示键数组补
  `ENGINE EXTRA_ENGINE_ARGS HOST_ENGINE_PATTERN`（行号见施工图）。
* `tests/host_templates_selftest.sh`：`EXPECTED_TEMPLATES` 追加新模板；
  `DRY_EXPECT_DESC` 为每个引擎模板加"serve_launch.sh 必含片段"断言；
  新增一条守卫：`ENGINE=strata RUNTIME=docker` dry-run 必须 die 且文案含 "docker"。

## 10. 迁移路径（与 DeepSeek 部署栈施工图的关系）

* 本接口先施工：DeepInfer 按 F1 契约注册（`engines/deepinfer.sh` + `hosts/engine/deepinfer.env`），
  《../施工图-DeepSeek部署栈支持.md》的 T2.1/T2.2 相应作废、T2.3–T2.7 语义不变。
* 该图先施工：本文施工图需**追加一个迁移任务**（把 `case "$ENGINE"` 分支收拢进注册表、
  把该图的 `ENGINE`/`DEEPINFER_ACCELERATOR` 键并入 T1.2 的三处同步），`engines/deepinfer.sh`
  由迁移产出。
* DeepEP 任何阶段都不受影响（增强型组件走模板层的裁定不变）。
